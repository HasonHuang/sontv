# IPTV 分发架构与部署方案

本文给出「大陆终端 → CDN → 海外 VPS」链路下的服务架构、组件落位、伪装实现与部署步骤。

**数据来源标注**
- 🟩 **实测** — 2026-10-04 于 `localhost:9100`（CharmingStreamer v1.4.1 容器）验证伪装行为；2026-10-05 用真实 IPTV-API 源验证 Provider 导入与自定义保留
- 📖 **手册** — `docs/CharmingStreamer/`（v1.4.1）、`docs/iptv-proxy/`（v0.8.2，采集 2026-10-02/03）
- 🌐 **上游** — `github.com/Guovin/iptv-api` 的 README（`master` 分支）
- ⚠️ **推断** — 工程推理，标注处需在真实链路上验证

## 1. 容量账

### 1.1 两台机器

| 机器 | 配置 | 角色 |
| --- | --- | --- |
| 海外 VPS | 1C / 64–128MB | **媒体出口**：反代 + 伪装 + CDN 回源 |
| 大陆 VPS | 2C / 2GB | **控制面**：源检测 + 目录 + 用户 + EPG。零媒体流量 |

### 1.2 各组件内存

| 组件 | 内存 | 依据 | 64MB 海外 | 128MB 海外 |
| --- | --- | --- | --- | --- |
| IPTV Proxy | **约 10MB**（实测） | ⚠️ 你的实测，见下 | ✅ | ✅ |
| IPTV Proxy（开缓存） | 📖 28MB 空闲 / 71MB(1观众) / 89–117MB(5观众) | `resource.md` | ❌ | ⚠️ 观众多时 OOM |
| nginx | ⚠️ ~10–20MB | worker×buffer 决定 | ✅ | ✅ |
| sontv | 🟩 **O(32KB)/请求** | README：8KB 探测块、`io.Copy` 透传 | ✅ | ✅ |
| CharmingStreamer | **60MB+** | 题设 | ❌ | ❌ |

### 1.3 关于 IPTV Proxy 的两个测量

数值差了一个量级，需要说明：

| 来源 | 数值 | 条件 |
| --- | --- | --- |
| 📖 `resource.md` | 28MB 空闲 → 117MB（5 观众） | Docker 容器，缓存后端 `disk`，伪装开启，**未开** Token/预载/录制/EPG |
| ⚠️ 你的实测 | 约 10MB，多并发 | 条件未知 |

差异最可能来自**缓存后端与内存上限**。`resource.md` 明确写了「每观众约 15–22 MB」的增量全部来自缓存。

**处理方式**：以你的实测为准做规划，但在目标机上复测一次：

```bash
# 起动后
docker stats --no-stream --format '{{.MemUsage}}' iptv
# 5 个不同频道并发播放 10 分钟后
docker stats --no-stream --format '{{.MemUsage}}' iptv
# 系统设置 → 缓存配置 → 内存上限，建议设为 32MB
```

若 5 观众档位超过 50MB，把海外升到 128MB 以上。

### 1.4 结论

**海外装得下 IPTV Proxy，装不下 CharmingStreamer。** 这是全部架构的起点。

## 2. 硬约束

### 2.1 大陆 VPS 无法直连海外 VPS

| 判断 | 结论 |
| --- | --- |
| 海外媒体到大陆能否绕开 CDN | 不能 |
| 大陆 VPS 能否代理海外源 | 不能 |
| 大陆 VPS 能处理什么 | ① 大陆可直连的上游；② 纯文本资产 |

**推论 A**：海外的任何媒体输出必须挂在 CDN 域名下。

**推论 B（单向）**：「大陆 → 海外」不通，不等于「海外 → 大陆源」不通。**海外可以完整抓取 IPTV-API 的产物**（它是公开的静态文件）。

**推论 C**：大陆能访问 CDN，但访问不到源站 IP。**大陆可以消费海外经 CDN 发布的任何东西**——这让大陆侧做聚合成为可能（§4.4）。

### 2.2 CDN 不支持视频流

伪装需三件事同时成立：URL 后缀是图片格式、响应头 `Content-Type: image/*`、分片路径不重复。

## 4. 核心问题：CharmingStreamer 能否统一管理订阅与节目

### 4.1 结论

**可以。你的两个场景都成立。**

🟩 实测（2026-10-05，用真实源 `https://iptv.ihason.com/m3u?token=…`，目录 484 条 / 32 分类 / 258 个唯一频道名）：

| 场景 | 结果 |
| --- | --- |
| 不做任何改动，用户拿到的内容与 IPTV-API 一致 | ✅ |
| 删掉几个频道 | ✅ 触发同步后**没有复活** |
| 改频道名 | ✅ 保留 |
| 改分类（`category`） | ✅ 保留 |
| 新增频道 + 新建分组 | ✅ 保留 |
| 调整频道顺序 | ✅ 保留 |

**机制**：同步改的是 Provider 自己的那份上游副本，不是你的频道。详见 §4.2 的三张表。

### 4.2 「目录」是什么

本文里的「目录」指 **Provider 对上游 m3u 的一份本地副本**，不是文件系统目录。

🟩 三者是三张独立的表（`sqlite3 /app/var/mpd-hls.db` 实测）：

| 表 | 当前行数 | 是什么 | 谁会改它 |
| --- | --- | --- | --- |
| `m3u_accounts` | 1 | Provider 账号（订阅源本身） | 你手工建 |
| `m3u_channels` | 121 | **Provider 的目录**：上游 m3u 解析后的条目，带 `category` / `epg_channel_id` / `logo` | **只有「同步目录」会改** |
| `channels` | 55 | 真正在播的频道，参与分发、EPG、订阅生成 | 手工编辑，或从目录「导入」 |

两个动作分别做什么：

```
「同步目录」  抓上游 m3u → 重新解析 → 全量重建 m3u_channels 里属于该 Provider 的行
             ↓
             不碰 channels 表。已完成的自定义毫发无损。

「导入」      从 m3u_channels 里挑若干行 → 复制成 channels 的新行
             ↓
             复制，不是引用。两边就此脱钩。
```

**这就是「重复导入不去重」的根本原因**：导入是复制操作，每次都新增行，从不回头比对更新已有行。同一段内容在目录里有几条（🟩 实测 CHC动作电影 有 2 条目录条目，`source_url` 完全相同），就会变成几个频道。

### 4.3 Provider 的正确定位：一次性导入 + 只读目录

这是本方案最容易被误解的一点。

> **Provider 不是持续同步管道。它在一次性导入之后降级为「只读目录」。**

频道的日常维护全部靠手工。目录的唯一用途是：**当 IPTV-API 新增了频道时，你去目录里挑出来导入。**

### 4.4 三个导入时必须知道的机制

🟩 均为实测。

**① 导入不建分组，但 `group-title` 会保住**

Provider 导入的 payload 是 `{channel_ids, group_id, delivery_mode, on_demand, overwrite_category}`，**没有** `auto_create_groups_from_category`——所有频道进同一个 CharmingStreamer 分组。

但订阅输出的 `group-title` 取自频道的 `category` 字段（留空才回退到分组名），所以播放器里看到的分组**完全正确**。

| 步骤 | 结果 |
| --- | --- |
| Provider 同步 | `category_count: 32` |
| 导入后的频道 | 全部在一个分组 |
| 频道的 `category` | 带住了原 `group-title` |
| **订阅输出** | **`group-title` 与 IPTV-API 完全一致** |

> 一次性「导入 m3u」**有**「按 group-title 分组」选项，会创建/匹配分组。Provider 导入没有。两者不要混淆。

**② 必须勾 `overwrite_category: true`**

这是把 `group-title` 带进 `category` 的开关。不勾，32 个分类会塌成一个。

**③ 重复导入不去重 —— 硬约束**

把一个改过名的频道从目录再次导入：

```
7358b690  CHC动作电影          src=http://198.204.228.26/live/chcdz.m3u8   ← 新建
25461475  CHC动作电影(已改名)   src=http://198.204.228.26/live/chcdz.m3u8   ← 原有
```

**`source_url` 完全相同，仍是两条独立记录。** 导入只新增，不更新。

### 4.5 工作流

| 阶段 | 动作 |
| --- | --- |
| **一次性** | 建 Provider → 同步目录 → 按分类筛选 → 导入（勾 `overwrite_category`） |
| **一次性** | 导入后全选 → 「启用 302 下发」 |
| **日常** | 手工增删改排序。同步不碰 |
| **定期** | 打开 Provider 目录看有无新增。**先搜现有频道确认不存在，再导入** |

**去重是手工的责任。** 目录里 484 条对应 258 个唯一频道名，平均每频道 1.88 个接口，35 个频道有 5 个以上（CCTV-1 有 5 个）。全量导入会让播放器里出现大量同名条目。

**建议**：导入时按分类筛选，或每个频道只导第一条接口。

### 4.6 进口侧：两个 Provider 一次合并

| Provider | 来源 | 频道 | 分发模式 | 终端访问 |
| --- | --- | --- | --- | --- |
| `direct` | IPTV-API `/m3u` 端点 | 80%+ 大陆可直连 | **302 下发** | 源站（不经我方） |
| `hongkong` | 海外 IPTV Proxy 订阅（**经 CDN**） | 港澳频道 | **302 下发** | CDN → 海外 |

第二行靠的是**推论 C**：大陆访问不到源站 IP，但访问得到 CDN。海外订阅挂在 CDN 域名下，大陆的 Provider 就能拉到。拉下来的地址已经是 CDN 地址，CharmingStreamer 原样交给终端，**它自己一次都不取**。

### 4.7 IPTV-API 的接入方式

**不需要任何 Python 脚本。** IPTV-API 本身就是 Python，且对外提供 HTTP 端点：

| 端点 | 内容 |
| --- | --- |
| `/m3u` | **m3u 格式，用这个** |
| `/txt`、`/` | txt / 默认格式 |
| `/ipv4/m3u`、`/ipv6/m3u` | 按协议分组 |

直接填 `http://<大陆 VPS>:<端口>/m3u?token=…`。

> ⚠️ 配置项 `final_file` 的默认值是 `output/result.txt`，那是 `频道名,URL` 的自定义格式，**CharmingStreamer 不认**。用 HTTP 端点而不是读那个文件。

### 4.8 已知代价

| 代价 | 说明 | 应对 |
| --- | --- | --- |
| **新增频道不自动进来** | IPTV-API 加了频道，CharmingStreamer 不会自动有 | 定期看目录，手工导入（先搜重） |
| **导入不去重** | 同 `source_url` 会产生两条频道 | 导入前先搜 |
| **目录有两份** | IPTV-API 是源头，CharmingStreamer 是副本 | 想改别名改 IPTV-API |
| **tvg-id 丢失** | 见下 | EPG 绑定页处理 |

### 4.9 tvg-id 不随导入带过来

🟩 实测：Provider 目录里读到了 `epg_channel_id`（IPTV-API 的 `tvg-id="翡翠台"`），但**导入后的频道对象上没有这个字段**，订阅输出退化成 `tvg-id="stream-<uuid>"`。

`source_url`、`logo`、`name` 都完整带过来了，**只有 tvg-id 丢了**。

📖 §12 的 EPG 绑定页有 `自动 / 手动 / 未绑定` 三态徽章，说明自动匹配存在——**只有对不上的才要手工绑**。工作量是「看未匹配报告」而非逐频道手工。

> 📖 `/api/epg/rules`（关键字规则）是「节目标题命中关键字 → 自动预约推流/录制」，**不是**自动绑定，别指望它省这一步。

### 4.10 什么情况下不该用这个方案

| 情况 | 替代做法 |
| --- | --- |
| 不需要按用户/按设备区分订阅 | 直接用海外 IPTV Proxy 单独出订阅，少一个组件 |
| 期望频道随 IPTV-API 自动增减 | 本方案不支持。目录只能看不能自动同步 |
| 需要 CharmingStreamer 独占的 DRM 解密 | 加密源仍需它处理，但它在大陆只能服务大陆可直连的源 |
| 观众很多且带宽敏感 | 见 §6.3——IPTV Proxy 的 CDN 缓存优势成立，但要确认终端只从海外取媒体 |

## 5. 节目分流

### 5.1 决策表

| 频道 | 检测结果 | 处理位置 | 分发模式 | 终端访问 | 海外带宽 |
| --- | --- | --- | --- | --- | --- |
| IPTV-API 公共源（80%+） | 大陆可直连 | 不代理 | 302 下发 | 源站 | **0** |
| 港澳频道 | 需反代 | 海外 IPTV Proxy | Proxy + 伪装 | CDN → 海外 | 全量 |
| 手工 · 明文 HLS | 视检测结果 | 同上两行 | — | — | — |
| 手工 · **加密源** | — | ❌ **做不到** | — | — | — |

### 5.2 分流开关在哪

| 层级 | 位置 | 粒度 |
| --- | --- | --- |
| 大陆可直连与否 | IPTV-API 定时检测 | 频道 |
| 直连 → 302 | CharmingStreamer 频道行「启用 302 下发」 | **频道** |
| 反代 → 伪装 | 海外 IPTV Proxy 分组「工作模式 = Proxy」 | 分组 |

📖 IPTV Proxy 的工作模式只能设到分组，同组共用。港澳频道全部同源同向，分组粒度够用。

### 5.3 加密源：小鸡放不下

IPTV Proxy 的 DASH 模式与 CharmingStreamer 都需要 60MB+ 常驻内存。**64/128MB 的海外机器做不了加密源的反代。**

| 选项 | 代价 |
| --- | --- |
| A. 海外升配到 ≥1GB | 花钱 |
| B. 加密源也检测可直连，走 302 | 前提：源大陆可直连 |
| C. 放弃加密源反代 | 少一批频道 |

**这是唯一的实质功能损失。** 你的 IPTV-API 已经在检测可直连性——**如果加密源本身大陆可直连，选项 B 零成本**，检测结果会告诉你答案。

## 6. 图片伪装与 CDN

### 6.1 交给 IPTV Proxy 原生承担

🟩 实测确认 IPTV Proxy v0.8.2 的伪装设计**专为 CDN 而生**：

| 层 | 实现 | 是否改变字节 |
| --- | --- | --- |
| URL 后缀 | `png` `jpg` `gif` `bmp` `webp` 轮换 | 否 |
| Content-Type | `image/*` | 否 |
| 路径形状 | `<频道ID>_<切片内容哈希><假后缀>` | 否 |
| 载荷 | 原始 MPEG-TS，188 字节整包对齐 | 否 |

📖 字节级验证：四个后缀的同一切片前 32 字节逐字节相同，MD5 均为 `2eaaec995b0b757e003751021303a14`；28256 个包 `0x47` 命中率 100%；无 JPEG/PNG/WebP/BMP/fMP4 特征字节。

**nginx 在这里只做 TLS、CDN 回源入口和 IP 白名单，不需要做 sub_filter 改写。** 上一版方案里那套 nginx 伪装配置可以删掉。

### 6.2 分片命名：内容寻址，且不含令牌

这是 IPTV Proxy 相对 CharmingStreamer 的决定性优势：

```
分片：/hk/hbo/<频道ID>_<切片内容哈希>.png      ← 无令牌
主清单：/hk/hbo/index.m3u8?token=<稳定令牌>    ← 令牌在查询串
```

| 组件 | 分片路径含令牌 | CDN 缓存键 | 跨设备共享 |
| --- | --- | --- | --- |
| **IPTV Proxy** | ❌ 不含 | `/hk/hbo/<hash>.png` | ✅ **全网共享** |
| CharmingStreamer | 🟩 含 | `/l/<设备令牌>/video/<时间戳>.jpg` | ❌ 每设备一份 |

**结论：走 CDN 的媒体一律从 IPTV Proxy 出。** CharmingStreamer 的输出如果挂 CDN，缓存命中率趋近零（分片只出现一次，同一设备不重复拉），CDN 只剩代理作用，不省带宽。

🟩 附带数据：CharmingStreamer 的分片名是 Unix 毫秒时间戳（`1791109064091.jpg`），重启不复用，缓存安全性没问题——问题只在令牌位置。

### 6.3 带宽预算

```
海外出网 ≈ Σ(港澳频道码率) × (1 − CDN 命中率) × 时段重叠度
```

📖 `resource.md` 实测：**带宽是瓶颈，CPU 不是**。CPU 花在转发字节上，1 个用户看 4K 比 5 个用户看 720p 更费 CPU。

| 观众分布 | 命中率 | 效果 |
| --- | --- | --- |
| 都看同一批港澳频道，集中在少数边缘节点 | 高（接近 90%） | 出网降一个量级 |
| 分散看不同频道 | 接近 0 | 出网≈全量 |

因为只有港澳频道走海外，**总带宽比「全量海外代理」小得多**。50 Mbps 出网可支撑的并发：

| 场景 | 1080p / 6.2 Mbps |
| --- | --- |
| 10 路全看不同频道，命中率 0 | 约 8 路 |
| 10 路集中看 3 个频道，命中率高 | 视命中率而定，通常够用 |

### 6.4 CDN 配置

| 项 | 值 | 原因 |
| --- | --- | --- |
| 回源地址 / Host | `origin.example.com`（**不套 CDN**） | 回源走 CDN 会绕环 |
| 缓存规则（假后缀） | 匹配 `*.png` `*.jpg` `*.webp` `*.gif` `*.bmp` → **遵循源站** | 见下方红线 |
| 缓存规则（清单） | `*.m3u8` → Edge TTL 2–5 秒 | 直播清单必须短缓存 |
| 缓存规则（订阅） | `*.m3u` `epg.xml.gz` → 30 秒 – 数分钟 | 体量小，回源收益大 |
| 图片优化 | Polish / Mirage / 格式转换 **全关** | MPEG-TS 伪装成图片，任何图片处理都会失败 |
| 自动改写 | HTML/JS 改写关闭 | 同上 |

**红线**：📖 IPTV Proxy 的 `Cache-Control` 是 `public` → `private` 的窗口设计（`max-age=300`）。首访返回 `public` 让 CDN 收下，之后返回 `private` 让 CDN 不再存储。

- ❌ 不开「忽略源站 Cache-Control」——会把 `private` 当 `public`，直播分片被长期缓存，**播到旧画面**
- ❌ 不设「浏览器缓存 TTL」强制覆盖——与窗口冲突

### 6.5 已知边界

| 项 | 值 | 影响 |
| --- | --- | --- |
| `Range` 请求 | 📖 忽略，返回 200 + 全量 | 部分播放器起播慢、无法拖动 |
| `Accept-Ranges`/`ETag`/`Last-Modified` | 📖 均无 | 同上 |
| 单分片大小 | 📖 5312128 字节 ≈ 5.06 MB | 远低于 CDN 单文件上限 |
| 单文件上限 | CDN 免费版 100 MB | 无压力 |
| 上级面板 19899 | 绑 `127.0.0.1`，防火墙不放行 | 必须 |

## 7. 部署方案

### 7.1 端口与域名

| 位置 | 端口 | 绑定 | 用途 |
| --- | --- | --- | --- |
| 海外 | 443 | `0.0.0.0` | nginx，只接受 CDN 回源段 |
| 海外 | 19899 | `127.0.0.1` | IPTV Proxy 面板与播放 |
| 大陆 | 9100 | `0.0.0.0` | CharmingStreamer 面板与播放 |
| 大陆 | 80/443 | `0.0.0.0` | IPTV-API + 订阅 / EPG 出口 |

| 域名 | 解析 | 用途 |
| --- | --- | --- |
| `origin.example.com` | **A 记录直指海外 VPS IP**（不套 CDN） | CDN 回源 |
| `cdn.example.com` | CDN CNAME | 播放器看到的媒体域名 + 海外订阅 |
| `sub.example.com` | A 记录指大陆 VPS | 订阅、EPG |

### 7.2 海外 VPS

```bash
# IPTV Proxy
bash <(curl -fsSL https://raw.githubusercontent.com/YanG-1989/rust/main/IPTV%20Proxy/iptv-proxy.sh)
# 装完立刻改默认密码：iptv-proxy pass <新密码>
```

IPTV Proxy 配置：

| 项 | 值 | 理由 |
| --- | --- | --- |
| 分组工作模式 | **Proxy** | 港澳频道需要反代 |
| 切片伪装 | **开启** | CDN 需要 |
| 访问范围 | 公开 | 分组内已有 token 控制 |
| 网络配置 → UA / Referer | 按源站要求填 | 源站常按 UA 放行 |
| 系统设置 → 缓存配置 | 内存上限 **32MB** | 小鸡上的硬约束 |
| `config.toml` | `token_enabled = true` | 上线前安全清单第一条 |
| 系统设置 → 监听地址 | `127.0.0.1:19899` | 面板不对公网 |

```nginx
# /etc/nginx/conf.d/origin.conf
server {
    listen 443 ssl http2;
    server_name origin.example.com;

    # 只放行 CDN 回源段,源站 IP 即使泄露也无法直接访问
    allow <CDN 回源 IP 段>;
    deny  all;

    ssl_certificate     /etc/letsencrypt/live/origin.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/origin.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:19899;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;              # 直播分片不要缓冲
        proxy_read_timeout 60s;
    }
}
```

`proxy_buffering off` 是必须的。开着会让 nginx 攒够缓冲区再发，直播延迟从秒级涨到十几秒。

**防火墙**：只放行 443 与 SSH。19899 绑 `127.0.0.1`。

### 7.3 大陆 VPS

```bash
# IPTV-API
git clone https://github.com/Guovin/iptv-api.git /opt/iptv-api
# 按其文档配置定时任务。用 HTTP 端点 /m3u,不要读 output/result.txt

# CharmingStreamer
docker run -d --name mpd-hls --restart unless-stopped \
  -p 9100:9100 -p 1935:1935 \
  -v /opt/mpd-hls/var:/app/var \
  charmingcheung000/mpd-hls:latest

# 防火墙：阻断到海外 IP 段的出站,让误配置立刻暴露
sudo iptables -A OUTPUT -d <海外 VPS IP> -j REJECT
```

CharmingStreamer 配置顺序：

| 步骤 | 动作 | 注意 |
| --- | --- | --- |
| 1 | 建两个分组：`direct`、`hongkong` | 📖 分组名不进订阅地址，可以随时改 |
| 2 | 建 M3U Provider `direct` → `http://<大陆>:<端口>/m3u?token=…` | 设刷新间隔（建议 6 小时） |
| 3 | 建 M3U Provider `hongkong` → `https://cdn.example.com/<海外订阅路径>` | **必须是 CDN 域名**，大陆访问不到源站 IP |
| 4 | 同步目录 → **按分类筛选后导入** | 勾 **`overwrite_category`**，否则 32 个分类塌成一个 |
| 5 | 全选 `direct` 分组 → **启用 302 下发** | 一次性动作 |
| 6 | 建用户 → 按设备发令牌 | 📖 §15.3，不要一人一个令牌 |
| 7 | EPG 配置 + 频道绑定 | 看「未绑定」报告，不是逐频道手工 |

**第 3 步是这个方案的枢纽。** 若填源站 IP 或海外裸域名，大陆拉不到，Provider 同步会失败。

**第 4 步不要全量导入。** 目录 484 条对应 258 个唯一频道名（CCTV-1 有 5 个接口）。全导会产生大量同名条目，且**重复导入不去重**（§4.4）。

**Provider 在此之后只作只读目录。** 频道的增删改排序全部手工，同步不会覆盖（§4.1）。

📖 §15.3：旧式 `?u=&p=` 把用户名密码暴露在 URL 里且无法单独吊销，**不要分发**。

### 7.4 三份订阅的关系

| 订阅 | 地址 | 谁用 |
| --- | --- | --- |
| **最终订阅**（唯一发给用户） | `sub.example.com/...`（CharmingStreamer） | 播放器 |
| 大陆直连源清单 | IPTV-API 产物 | 只被 `direct` Provider 消费 |
| 港澳订阅 | `cdn.example.com/...` | 只被 `hongkong` Provider 消费 |

**只有第一份需要分发。** 另外两份是系统内部的输入。

## 8. 风险与备份

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| 1 | **海外加密源无法反代** | 该批频道不可用 | §5.3 三选一。IPTV-API 的检测结果会告诉你答案 |
| 2 | **IPTV Proxy 开缓存后内存飙升** | 海外 OOM | 内存上限设 32MB；海外升 128MB |
| 3 | CDN 忽略源站 `Cache-Control` | 播到旧画面 | §6.4 两条红线 |
| 4 | **磁盘写满** | 缓存停止写入 | 海外 VPS 配 `tmpfs` 存缓存，或定期清理 |
| 5 | 香港 Provider 填了源站 IP | 同步失败，港澳频道消失 | 必须是 CDN 域名 |
| 6 | **重复导入产生同名重复频道** | 播放器里一堆重复条目 | 🟩 导入不去重，导入前先搜（§4.4） |
| 7 | **全量导入 484 条** | 258 个频道变成 484 个同名条目 | 按分类筛选导（§4.5） |
| 8 | 目录双份，改错地方 | 别名不生效 | IPTV-API 是唯一编辑入口 |
| 9 | CDN 厂商禁止视频分发 / 未备案域名 | 接入被拒 | 厂商确认 |
| 10 | 源站 IP 经 DNS 泄露 | 可绕过 CDN 直打源站 | 防火墙只放行 CDN 回源段 |
| 11 | 源站不可达时海外拉不到自己的订阅 | Provider 同步失败 | 频率调低；海外订阅给长 TTL |
| 12 | IPTV Proxy 回源流量统计失效 | 面板读数误导判断 | 📖 已知问题，看 `docker stats` |
| 13 | 忘了勾 `overwrite_category` | 32 个分类塌成一个，播放器分组全乱 | 导入时必勾（§4.4） |

### 备份

| 组件 | 方法 | 陷阱 |
| --- | --- | --- |
| IPTV Proxy | 面板系统设置页下载完整备份 | 无 |
| IPTV-API | `config/` 目录 + 定时任务配置 | 检测结果可重新生成，不必备份 |
| CharmingStreamer | **`.db` + `-wal` + `-shm` 三个文件一起热拷**，或 `sqlite3 .backup` | 只热拷 `.db` 会丢数据。📖 实测 `-wal`（333 KB）比主库（274 KB）还大 |
| CharmingStreamer 配置 | `channels.json` / 脚本目录，都在 `/app/var/` 下 | 随 SQLite 一起备 |

## 9. 分阶段落地

### 阶段 0 · 确认加密源（地基）

跑一次 IPTV-API 的检测，看结果里有多少频道需要反代、其中有没有加密源。

**这一步决定海外要不要升配。** 你的架构已经假定「80%+ 直连」，先确认剩下的 20% 里有没有 DASH/DRM。

### 阶段 1 · 海外最小闭环

IPTV Proxy 装好，建一个港澳测试分组，Proxy + 伪装开启。用一台大陆终端**直连** `origin.example.com` 验证能播。

此时不开伪装，先确认代理本身通。

### 阶段 2 · 开启伪装并挂 CDN

按 §6.4 配 CDN，跑 §6.6 四项验证。四项全过再继续。

### 阶段 3 · 大陆聚合

装 CharmingStreamer，建两个 Provider。

**先确认 `hongkong` Provider 能拉到**——它是整个方案最容易断的一环。

然后同步 `direct` 目录，**按分类筛选后导入，勾 `overwrite_category`**。不要全量导（§4.5）。

### 阶段 4 · 用户与 EPG

建用户、按设备发令牌、配置 EPG。

**先看「未绑定」报告。** 🟩 自动匹配是存在的，只有对不上的才要手工绑。频道能播但节目单空白，八成是 `tvg-id` 没绑上（导入不会带过来，§4.9）。

### 阶段 5 · 观测一周

- [ ] 海外 VPS 出网带宽曲线
- [ ] 海外 VPS 内存峰值（`docker stats`）
- [ ] **CDN 分片缓存命中率**（决定要不要加带宽）
- [ ] 海外磁盘占用（缓存写满会静默停止）
- [ ] 两个 Provider 的同步是否稳定
- [ ] 大陆 VPS 侧确认零媒体流量（看网卡计数器）
- [ ] 订阅里的 `group-title` 是否与 IPTV-API 一致（抽查几个分类）

## 10. 已确认与待确认

### 已确认（🟩 实测，2026-10-05）

| # | 结论 |
| --- | --- |
| 1 | Provider 同步不影响已导入频道：删除、改名、改分类、增删、排序全部保留 |

| 8 | 伪装只在「转封装推流」模式生效；分片名为毫秒时间戳；载荷是原始 MPEG-TS |
