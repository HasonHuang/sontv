## 结论摘要
1. 伪装切片名 = `/{gid}/{cid}/<P>_<S>.<ext>`：`<P>` = **16 hex**，`<S>` = **32 hex**。
2. `<S>` = `sha256(上游切片绝对 URL)` 的**前 32 hex**（本项复验通过：`sha256("http://host.docker.internal:9999/seg0.ts")[:32]` 与观测一致）。
3. `<P>` **只依赖 `(gid, cid)`**：改频道 `name` → 不变；改频道 `url`（`x.m3u8`→`x2.m3u8`）→ 不变；换请求 `Host`（`127.0.0.1` / `192.168.215.4` / `example.com`）→ 不变；删缓存清单/映射后重取 → 不变（非随机、不落盘）。
4. `<P>` **参与校验**：错误/缺失/截短前缀 → **302**（占位）；正确前缀 → 200。扩展名**不参与校验**：`…_<S>.png` 与 `.jpg` 返回同字节。
5. 已**排除**的推导（对 3 个已知样本同时不成立）：`sha256/md5/sha1/sha512/blake2b/blake2s`（任意 16 位窗口）、`xxh3-64`、`xxh64`、`xxh32`、`fnv1a-64`、`fxhash-1`、`crc64`、`SipHash-1-3(k=0)`、`mmh3`、`CityHash64`、`UUIDv3/v5`（DNS/URL/OID/X500/nil）。输入模板覆盖：分隔符拼接（`"" / _ : - | . NUL \n :: @ # 空格 __ // + & = ,` 等）、前后缀、长度前缀（u8/u32/u64 LE/BE）、JSON、Rust `Debug` 元组/结构体、配置下标。
6. **功能影响低**：客户端始终从清单取得 `<P>`，无需自行推导；重建实现可自选前缀方案（只要自洽校验）。

## 1. 形状与实例

```text

test1/c1 → …/test1/c1/ea8680a1b61c17e4_e4b50304d62739a7b6df027f7cfc3155.jpg
test1/c2 → …/test1/c2/8cb3e469c0dd0aa3_e4b50304d62739a7b6df027f7cfc3155.png
g2/c1    → …/g2/c1/5ae12330d3e32594_e4b50304d62739a7b6df027f7cfc3155.png

```

- 三条记录的上游均为 `x.m3u8`，首切片均为 `seg0.ts` → `<S>` 相同、`<P>` 不同；内部缓存键另见 `cache/seg_url/<P>_<S 前 3 位>__<32hex>`（该 32-hex 与 `<S>` 无关，映射条目哈希）。

## 2. 输入依赖实验

| 变更 | 结果 |
| --- | --- |
| 频道 `name`：`C1` → `C1Z` | `<P>` 不变（`ea8680a1b61c17e4`） |
| 频道 `url`：`x.m3u8` → `x2.m3u8` | `<P>` 不变 |
| 请求 `Host`：`127.0.0.1` / `192.168.215.4` / `example.com` | `<P>` 不变 |
| 删除 `cache/m3u8/test1_c1__*` 与 `cache/seg_url/<P>_*` 后重取 | `<P>` 不变 |
| 进程重启（历史多轮） | `<P>` 不变 |

结论：`<P> = F(gid, cid)`，纯确定性函数，不含请求期状态。

## 3. 校验行为

```text

GET /test1/c1/ea8680a1b61c17e4_e4b5….jpg   → 200（1880 B）
GET /test1/c1/0000000000000000_e4b5….jpg   → 302（占位）
GET /test1/c1/ea86_e4b5….jpg               → 302
GET /test1/c1/e4b5….jpg                    → 302
GET /test1/c1/ea8680a1b61c17e4_0000….jpg   → 302
GET /test1/c1/ea8680a1b61c17e4_e4b5….png   → 200（同字节）

```

- 前缀**必须**匹配；后缀**必须**匹配；**扩展名任意**。与 S-DIS-05（后缀不校验）不冲突：S-DIS-05 指“清单写 `.png`、请求 `.jpg`”；此处 `<S>` 本身仍须正确。

## 4. 排除记录（方法）
对每个候选输入 `x` 与候选哈希 `H`，要求同时满足三类样本：

```text

H(x(gid,cid)) 的前 16 hex（或任意 16 位窗口 / 后 16 位） == <P>

```

候选集合（约 2 万组合）：
- 组件：`gid, cid, name, url, entry_url, path, "gid_cid", host, 配置下标`；组合：1–3 个组件的排列；分隔符 22 种（含 `\0`、`\n`、`\t`、`::`、`__`、`//`）；前后缀 20 种（`channel:`、`v1:`、`seg:`、`entry:` 等）。
- 结构形态：JSON（对象/数组）、Rust `Debug` 元组/结构体、长度前缀（u8/u32/u64，LE/BE）；哈希列表见结论摘要第 5 条。
全部不成立。**推断**：`<P>` 使用了非标准输入（例如固定盐/密钥的 HMAC，或自定义序列化），或在 64 位哈希后做了额外变换。

## 5. 复现

```bash

B=http://127.0.0.1:19899
S=e4b50304d62739a7b6df027f7cfc3155
curl -s -o /dev/null -w '%{http_code}\n' "$B/test1/c1/ea8680a1b61c17e4_$S.jpg"   # 200
curl -s -o /dev/null -w '%{http_code}\n' "$B/test1/c1/0000000000000000_$S.jpg"   # 302
curl -s -o /dev/null -w '%{http_code}\n' "$B/test1/c1/ea8680a1b61c17e4_$S.png"   # 200
# 输入依赖：改 name / url / Host 后重取清单，观察 <P> 不变（见 §2）

```

## 5.1 2026-10-24 补充样本与排除

在 amd64 目标实例 `rea82v09` 上用新分组复验，前缀仍只随 `(gid, cid)` 变化：

| `gid` | `cid` | `<P>` |
| --- | --- | --- |
| `x1` | `c1` | `60b602c374f3a606` |
| `x1` | `c2` | `ca76db14a9439069` |
| `x2` | `c1` | `932372bc20b32221` |
| `x_3` | `c-4` | `dcab9780a2f16d50` |
| `ts1` | `c1` | `6dc0662aa670c0f7` |

复验条件：

- 改分组名、频道名、频道 URL 后 `<P>` 不变。
- 删 `/cache/m3u8/<gid>_<cid>__*` 与 `/cache/seg_url/<P>_*` 后重启，`<P>` 不变。
- 请求 `Host` 变化不影响 `<P>`。

新增排除：

- 对 5 个样本同时尝试约 **2005** 种 `(gid,cid)` 模板（22 种分隔符、前后缀、路径、`.m3u8`/`.ts` 等），配合 MD5/SHA-1/SHA-2 族/BLAKE2/xxHash/mmh3 的任意 16 位窗口与大小端变换，均不匹配。
- 尝试 `hash(gid) XOR hash(cid)`、相加/相减、Rust `DefaultHasher` 的元组/字符串拼接/XOR 组合，均不匹配。
- 脱壳二进制为 stripped Rust；cargo-auditable 依赖表为空。内嵌 crate 列表未见独立哈希 crate（有 `ring`、`hex`、`uuid`），因此无法仅凭 crate 名确定算法。
- 目标字符串中的 `filename prefix must be a valid UTF-8 string` 属于日志滚动文件名，与切片 `<P>` 无关；未找到可用的格式化串或常量盐。

**结论不变**：低影响差异。客户端只从清单读取 `<P>`；重建实现使用自洽的 `sha256("<gid>:<cid>")[:16]` 即可。继续黑盒穷举的收益低于成本。

## 6. 未决 / 局限
- `<P>` 的**具体算法未解**（负结果已覆盖主流哈希族与输入模板）。
- 只验证 `proxy` 模式；`dash`/`rewrite` 的前缀是否同构未逐一对照（形状一致，见 S-DIS-12）。
- 未做 32/64 位哈希的字节序变换穷举（如按大端读取再格式化）。
- 未使用反汇编定位（ELF 已 strip；REA 的 ELF 布局工具仅支持 Linux x64），后续可用 rizin/Ghidra 定点分析。
