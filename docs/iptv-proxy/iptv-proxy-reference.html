📺 IPTV Proxy 使用文档

IPTV Proxy 是一个直播流代理服务。它把直播源中转一遍，播放器只跟你的服务器通信。

文档基于 v0.8.2 实机采集写成。采集日期：2026-10-02。

三分钟跑起来

在服务器上执行这一条命令：

bash <(curl -fsSL https://raw.githubusercontent.com/YanG-1989/rust/main/IPTV%20Proxy/iptv-proxy.sh)

选择 1 开始安装。安装程序询问四个问题。直接按回车键接受默认值。

问题默认值
端口19899
账号admin
密码admin

然后在浏览器中打开面板，导入订阅，复制订阅地址。

详细步骤见 订阅接入入门。执行时间约 15 分钟。

⚠️ 安装完成后必须改密码。默认密码是公开的。

六种工作模式

模式设置在 分组管理 → 编辑分组 → 工作模式。同一分组内所有频道共用该模式。

项目的 README 文件写有四种模式。面板实际提供六个选项。

两个常见错误

订阅聚合不做反向代理

订阅聚合的频道在总订阅中保留上游原始地址。播放器直接连接源站。这些频道无法使用 Token、缓存和录制。

要使用反向代理，请用 分组管理 → M3U 导入。

M3U 导入不接受订阅地址

M3U 导入的窗口只接受粘贴内容和上传文件。窗口内没有填写地址的输入框。

能填写地址的是订阅聚合页。但该页面不做反向代理。

详细说明见 订阅接入入门。

IPTV Proxy 订阅接入入门

你的情况：你有一份或多份 M3U 订阅。你希望流量经过自己的服务器（反向代理）。然后把订阅地址填入播放器。

本文的执行时间约 15 分钟。

⚠️ 面板的「订阅聚合」功能不做反向代理。 该功能只合并订阅，并保留上游地址。 「M3U 导入」功能提供反向代理。参见开头的对比表和第 6 步。

先看这里：两种导入方式的区别

面板提供两个导入功能。请根据目标选择。

项目M3U 导入订阅聚合
输出地址✅ 代理地址❌ 上游原始地址
适用目标流量经过自己的服务器合并多份订阅
频道存储保存到你的分组不保存。生成总订阅时拼接
上游修改后需要重新导入自动更新
删除单个频道支持不支持
工作模式 / 缓存 / 录制 / Token✅ 支持❌ 不支持

⚠️ 实测结果（2026-10-02）：订阅聚合的频道在 /playlist.m3u 中输出上游原始地址。 手动添加的频道输出 http://localhost:19899/mygroup/HOY77.m3u8。 订阅聚合的频道输出 https://上游域名/...。 因此订阅聚合不等于反向代理。

⚠️ M3U 导入不接受订阅地址。 该窗口只接受粘贴内容和上传文件。 「订阅聚合」页接受订阅地址，但不做反向代理。

导入订阅前，先获取订阅内容。参见第 2 步。

选择建议：需要反向代理时，选择 M3U 导入。该功能把订阅转换为你的频道，并支持代理、删除和模式更改。

多份订阅：对每份订阅分别执行一次导入。每份订阅生成一个独立的分组。总订阅地址包含全部分组，全部经过代理。

三分钟速通

执行下列五步可以完成安装。

  • 安装 —— 选择 1，按回车键接受默认值
  • 登录 —— 打开 http://服务器IP:19899/panel，使用 admin / admin
  • 导入 —— 分组管理 → M3U 导入 → 粘贴订阅内容或上传文件 → 频道模式 Proxy → 导入策略 追加 → 开始导入
  • 复制地址 —— 分组管理 → 复制订阅地址。每个分组各有一条
  • 填写地址 —— 在播放器中填写该地址

总订阅地址包含全部分组：http://服务器IP:19899/playlist.m3u

完成上述步骤后，阅读后续章节了解细节。

第 1 步：安装

bash <(curl -fsSL https://raw.githubusercontent.com/YanG-1989/rust/main/IPTV%20Proxy/iptv-proxy.sh))

选择 1 开始安装。安装程序询问四个问题。按回车键接受默认值。

问题默认值
面板端口19899
面板账号admin
面板密码admin

安装目录是 /opt/iptv-proxy。服务自动设置为开机自启。 在浏览器中打开 http://服务器IP:19899/panel，使用 admin / admin 登录。

⚠️ 两件马上要做的事

  • 更改密码 —— 执行 iptv-proxy pass 你的新密码。改完后需要重新登录
  • 放行端口 —— 面板默认监听所有网卡。在云安全组和防火墙中放行 19899

第 2 步：把你的订阅导进来

打开 分组管理，点击顶部的 M3U 导入。

该窗口只包含「选择文件」和「M3U 文本」两个输入框。窗口内没有订阅地址输入框。 请先获取订阅内容。

方式操作

订阅地址返回一份文本文件。第一行是 #EXTM3U。内容较多时，下载文件更方便。

执行导入

输入项内容
选择文件 / M3U 文本上一步获取的文件或内容。二选一
频道模式Proxy
导入策略追加

点击「开始导入」。等待数秒。频道显示在分组列表中。

需要自动更新时： 使用「订阅聚合」页。该页接受订阅地址，但不做反向代理。参见开头的对比表。

频道模式怎么选

选项使用条件
Proxy默认选择。支持缓存、回看、录制
Rewrite只改写播放列表地址。出网流量为零。不支持缓存
Redirect返回 302 跳转。出网流量为零。源地址对播放器可见

不确定时选择 Proxy。导入后可以更改。

导入策略

策略行为
追加跳过同名分组。新分组追加到列表。推荐
合并保留同名分组。新频道加入该分组

导入后会自动处理的东西

导入程序自动完成下列处理：

  • 频道名称、tvg-id、分组标题等元数据全部保留
  • UA / Referer / Origin 等请求头自动抓取
  • 源站地址里的相对路径自动补全

⚠️ 部分频道导入后无法播放。 部分源站校验 Referer 等请求头。参见第 5 步。

第 3 步：拿到订阅地址

单个分组地址

在分组列表中，点击分组右侧的复制按钮。

http://你的IP:19899/分组ID/playlist.m3u

总订阅地址

该地址包含全部分组。多份订阅导入后使用该地址。

http://你的IP:19899/playlist.m3u

访问范围设为「隐藏」的分组不出现在总订阅中。该分组的独立地址仍然可以访问。

第 4 步：自定义顺序

面板支持三种排序方式。各自的可调整范围不同。

排序对象支持调整操作方式
分组内的频道✅展开分组，拖动频道
订阅源的优先级✅在订阅聚合页点击 ↑ / ↓ 按钮
分组之间的顺序❌面板未提供该功能

顺序决定优先级。 订阅聚合中靠前的源优先采用。多个源提供同名频道时，靠前的源生效。

第 5 步：让频道真的能播

导入后尝试播放频道。无法播放时，按下列顺序检查。

检查源地址

在 VLC 中打开原始订阅地址。可以播放则源地址正常。无法播放则源站故障。IPTV Proxy 无法处理源站故障。

检查工作模式

打开「分组管理」编辑分组，选择「工作模式」。

源的类型工作模式
.m3u8（HLS）Proxy / Rewrite / Redirect
.mpd（MPEG-DASH）DASH
.flv / .ts 连续流Remux

工作模式与源类型不匹配时，频道无法播放。

添加 UA 和 Referer

部分源站校验请求头。这是导入后无法播放的常见原因。

编辑分组或频道，打开「网络配置」。

字段填写条件示例值
User-Agent源返回 403 或错误页面时Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0 Safari/537.36
自定义请求头源校验 Referer 时点击「＋ 添加请求头」，每行一条，例如 Referer: https://源站域名/

在分组中填写，该分组的全部频道生效。在频道中填写，只对该频道生效。留空则继承分组的设置。

第 6 步：让订阅自动更新（不反代）

⚠️ 本节的功能不提供反向代理。 阅读后再执行。

订阅聚合的频道在总订阅中保留上游原始地址。播放器直接连接源站。流量不经过服务器。 因此无法使用 Token、缓存和录制，也无法隐藏源地址。

目标功能
流量经过服务器，支持缓存、录制、防盗链M3U 导入（第 2 步）
合并多份订阅，接受源地址可见订阅聚合（本节）

需要对两份订阅使用代理时： 对每份订阅分别执行一次 M3U 导入。 每份订阅生成一个独立的分组。总订阅地址包含全部分组，全部经过代理。 上游修改后，需要重新导入。

仅需要合并功能时，执行本节。

打开左侧导航的 订阅聚合，点击 + 添加订阅源，填写下列内容。

常见问题

Q：更改设置后没有生效？ 点击「保存设置」。热重载关闭时，执行 iptv-proxy restart。 下列三个开关在启动时读取，修改后必须重启服务：DASH 会话预启动、配置文件热重载监视、登录失败计数清理。 其余设置即时生效。

Q：播放器无法打开订阅地址？ 按顺序检查。 ① 启用 Token 验证时，地址必须包含 Token 参数。使用面板的「导出全部」获取地址，不要手工拼接 ② 频道的访问范围是否设为「隐藏」或「归档」 ③ 自己的 IP 是否在封禁列表中。检查安全管控页 ④ Token 是否过期

Q：频道可以播放，但没有节目单？ 检查 EPG 总开关。检查频道的 tvg-id。在「节目指南 → 频道匹配」查看「未匹配」数量。

Q：定时录制任务失败？ 原因是缺少 ffmpeg。面板的「视频素材」页显示检测结果。安装后重启服务。

Q：日志显示「边缘来源校验模式: Off」？ 该消息表示启用了边缘模式，但未配置密钥或未接受边缘请求。非 CDN 环境下该消息不影响使用。

Q：启用 Token 后旧地址是否有效？ 旧地址全部失效。启用前先分发地址。 启用后需要重新复制地址。

Q：为什么订阅聚合的频道不是代理地址？ 这是设计行为。订阅聚合只执行合并，不改写地址。使用 M3U 导入实现反向代理。参见开头的对比表。

Q：如何查看资源占用？ 面板「概览」显示实时指标。v0.8.2 的回源流量统计失效，数值始终为 0。 使用 docker stats 查看真实数据。参见 资源占用实测。

工作模式 · 反向代理（Proxy）

模式标识：proxy　|　面板位置：分组管理 → 编辑分组 → 工作模式

一句话：服务器替你拉流、缓存切片，再把切片转发给播放器。源地址对播放器不可见。

面板在模式选择框下方会显示这句官方说明：「清单与切片都经本服务转发并缓存，占带宽最高、最稳。」

数据怎么流

播放器  ──请求──▶  IPTV Proxy  ──拉流──▶  上游源站
   ▲                    │
   └──回传切片───────────┘
                 （切片同时落盘缓存，第二次观看不再回源）

播放器只和你的服务器说话，从头到尾不知道源站在哪。这就是 Proxy 存在的理由。

使用条件

场景说明
需要隐藏源地址频道链接被转发出去，源站地址不会暴露
需要缓存提速切片落盘，多人同时看同一频道时只有一次回源
源站限制并发或按 IP 鉴权所有请求都从你这一台服务器出去
想用本地回看 / 定时录制Proxy 和 Remux 是仅有的两种支持本地切片的模式
想开 Token 防盗链播放地址带 token，未授权请求直接被挡

不确定源是什么格式时的默认选择。 兼容性和功能覆盖都是最完整的。

不适用场景

  • 源站稳定且你不在意暴露地址 → Redirect 更省你的带宽
  • 源是 .mpd（MPEG-DASH）→ 用 DASH
  • 源是 .flv / .ts / MMT 连续流 → 用 Remux，别让 Proxy 硬扛
  • 服务器内存小 → Proxy 是最吃资源的模式，见下方「代价」

时间偏移到底怎么调

切片是按「录进来那一刻」打的时间戳，而直播本身有延迟，所以这个时间戳比节目实际播出的时间要快。

  • 放出来的是上一个节目的结尾 → 时间偏移调大
  • 放出来的是下一个节目的开头 → 时间偏移调小
  • 填 0 = 不偏移

例子：你按节目单点 20:00 的节目，播放出来是 19:55 那段的结尾，说明偏了 5 分钟，把偏移填 300（秒）。

两种方式：

方式 B · 批量导入（用来导整份订阅，推荐）

点顶部 M3U 导入 → 粘贴订阅内容或上传 m3u 文件 → 频道模式选 Proxy → 导入策略选 追加 → 开始导入。

⚠️ 这个弹窗不能填订阅地址，只接受文件或内容。地址要先下载成文件，或复制内容粘进去。 想直接填地址让它自动更新，用「订阅聚合」页。

详见 订阅聚合入门。

3. 补 tvg-id

导入后部分频道没有节目单。打开一个频道，把 tvg-id 填成节目单中的频道 id。

留空则用频道 ID，多数情况下匹配不上。

4. 复制订阅地址

分组列表右边点复制按钮，或直接拼：

http://你的IP:19899/live/playlist.m3u

5. 粘进播放器

TVBox / 影视仓 / TiviMate / Kodi 里填这个地址。

6. 播不了的话，按这个顺序查

  • 源本身能播吗 —— 把上游 URL 丢进 VLC。能播 = 源没问题，继续
  • 模式选对了吗 —— 源是 .mpd 要用 DASH，.flv/.ts 用 Remux
  • UA / Referer 填了吗 —— 源报 403 或返回错误页就是缺这个。见上面「网络配置」
  • Token 开了吗 —— 如果开了 Token，地址必须带 token 参数，用面板的「导出全部」而不是手工拼

7. 想回看的话

在频道的「回看保留时长」填小时数。留空 = 不录。

一个 1080p 频道每小时约 1~2 GB，先算算磁盘够不够。

代价

Proxy 是最吃资源的模式，因为流量真正经过你的服务器：

  • 出网带宽 = 所有观众的流量总和
  • 内存 = 缓存中的切片（可在系统设置里设上限）
  • CPU = 转发与缓存维护；预载开启时更高

要省资源：预载关掉、缓存后端改 memory 并设上限、缓存目录设硬盘上限。

实测占用

v0.8.2 实测（1080p / 6.2 Mbps 直播流）：

并发观众CPU（占单核）容器内存
1 个0.86%71 MB
2 个1.31%77 MB
5 个1.07 – 1.51%89 – 117 MB

决定 CPU 的是码率，不是人数；而同一频道多人共享缓存，5 人看同一个频道只占 0.51% 单核——比一个人还省。

真正的瓶颈是带宽：10 个观众看 6.2 Mbps 就是 62 Mbps 出网，比 CPU 重要一个数量级。

完整的换算方法、VPS 配置建议、内存控制开关、以及怎么自己测，见 资源占用实测。

💡 流量成本敏感的话，Proxy 不一定是最好的选择——Rewrite 和 Redirect 的出网接近于零。

排错

播不了 / 花屏 / 一直转圈

  • 源站地址能否直接在 VLC 里播？先排除源本身的问题
  • 网络配置里的 UA / Referer / Origin 是否填了？部分源站强制校验
  • 内容格式是不是选错了？源是 .mpd 就该用 DASH
  • 换 Redirect 试一下——如果 Redirect 能播，说明源没问题，是代理链路上有环节不对

能播但很卡

  • 预载开着？关掉试试
  • 缓存上限是不是太小，一直在淘汰又重新拉
  • 出口带宽是否已经跑满

回看时间点不对

  • 先确认「系统设置 → 时区」配对了（中国大陆填 8）
  • 再调频道的「时间偏移」，见上文

磁盘撑爆

  • 给频道设「最大磁盘占用」上限，或调小「回看保留时长」

想确认缓存有没有生效

  • 打开「缓存状态」页，看媒体片段数和磁盘占用是否在涨

工作模式 · Remux 转封装

模式标识：remux　|　面板位置：分组管理 → 编辑分组 → 工作模式

一句话：把 FLV、TS、MMT 这类连续流转封装成 HLS，不解码画面。注意：不需要解码，所以不吃 CPU。

面板的官方说明：「连续流(FLV/裸TS/MMT-TLV)实时切片成 HLS。容器默认自动识别,识别失败可手动指定。」

数据怎么流

播放器  ──请求──▶  IPTV Proxy  ──拉流──▶  上游（.flv / .ts / MMT）
   ▲                    │
   └──HLS 切片回传──────┘
              （只换封装，不解码 → CPU 开销极低）

使用条件

场景说明
源是连续流.flv、.ts、MMT 这些没有切片概念的流
源不支持 HLS，但播放器只吃 HLS转换封装后大多数播放器都能播
需要本地回看 / 定时录制Remux 和 Proxy 是仅有的两种支持本地切片的模式

不适用场景

  • 源已经是 .m3u8 → 用 Proxy 或 Rewrite，不需要转封装这一步
  • 源是 .mpd → 用 DASH
  • 只想隐藏源地址 → Proxy 更通用

Remux 与 Proxy 有什么区别

两者都能拉本地切片，但起点不同：

ProxyRemux
源类型已经是 HLS（.m3u8）连续流（FLV / TS / MMT）
处理动作转发 + 缓存转封装成 HLS
CPU 占用较高低（不解码）
预载配置有无
内容格式可选可选 HLS / MPD固定 HLS（转封装输出一定是 HLS）

一个历史坑：早期面板只给 Proxy 显示推流/回看区块，Remux 频道明明能本地录切片，界面上却只能填一个对它无效的「源站回看天数」。v0.6.9 修正了这点——现在 Remux 分组同样会显示推流/回看区块。

工作模式 · DASH 转封装

模式标识：dash　|　面板位置：分组管理 → 编辑分组 → 工作模式

一句话：把 MPEG-DASH（.mpd + .m4s 分片）实时转封装成 HLS，让只吃 HLS 的播放器也能播。支持 ClearKey 解密。

面板的官方说明：「DASH MPD 转封装为 HLS,可选 CENC ClearKey 解密。仅用于 .mpd 源。」

数据怎么流

播放器  ──请求──▶  IPTV Proxy  ──拉流──▶  上游（.mpd 清单 + .m4s 分片）
   ▲                    │
   └──HLS 切片回传──────┘
        （MPD → HLS 实时转封装；支持 ClearKey 解密）

使用条件

场景说明
源是 MPEG-DASH地址以 .mpd 结尾
需要给 HLS 播放器播放大量电视端和手机播放器只吃 HLS，DASH 源直连播不了
源用了 ClearKey 加密自动解密，这是 DASH 模式的主要卖点
需要多 CDN 故障切换自动的，不需要配

不适用场景

  • 源是 HLS（.m3u8）→ 用 Proxy，别给 DASH 模式喂 HLS 源
  • 源是 FLV / TS → 用 Remux
  • 怕配置复杂 → DASH 的调优项多，虽然默认值适配大多数源

DASH 模式自动化了什么

面板原文明确说明，这些不需要你配置：

  • 304 增量刷新——上游清单没变就跳过重新解析
  • 多 CDN 故障切换——主 CDN 挂了自动切备用
  • 防断流备份——上游意外断开时的兜底
  • 片段级容错——个别分片损坏不影响整体

真正要你动的是下面的高级参数，而面板的建议是：不确定用途就不要改，改错会直接影响起播与卡顿。

解决 CDN 单连接限流的问题。 默认关闭，需要时才开。

发片方式两种都是读本地已落盘的切片，差别只在这一片的字节要不要整块占住本进程内存。见下方详解带宽与人数需要权衡时见下

发片方式怎么选

选项内存表现适合
整片每个正在下载的连接占住一整片（1~2 MB）带宽大、人不多。高带宽高延迟链路上更能顶满发送窗口
流式每连接只留 64 KB 缓冲，内存与观看人数几乎无关人多或内存紧

判断方法：看仪表盘的「在线观众」。十来个人的小圈子用整片；几十上百人同时看就用流式。

上游源应该长什么样

http://upstream.example/dash/channel.mpd

确认是不是 DASH：

curl -sI http://upstream.example/dash/channel.mpd | grep -i content-type
# application/dash+xml  → 就是 DASH

也可以直接丢进 ffprobe：

ffprobe -v quiet -show_streams http://upstream.example/dash/channel.mpd

配置步骤

  • 分组管理 → 新建分组 → 工作模式选 DASH（MPD → HLS 转封装）
  • 新建频道，填上游 .mpd 地址、频道 ID、tvg-id
  • 源有 ClearKey 加密就填密钥，没有就留空
  • 想回看就填「回看保留时长」
  • 保存后复制订阅地址，导入播放器

M3U 批量导入时会自动识别：.mpd 开头的频道自动归为 DASH 模式。所以导入 DASH 订阅不用手改。

代价

  • 出网带宽 = 所有观众流量总和
  • CPU = 转封装 + 清单解析，比 Proxy 重
  • 内存 = 缓存的 MPD 与分片（用「整片内存预算」封顶）
  • 配置项最多，但默认值能覆盖大多数情况

排错

播不了 / 花屏

  • 源真的是 .mpd 吗？用 curl -I 看 Content-Type
  • 源的加密是不是 ClearKey？Widevine 需要额外处理
  • 频道的 ClearKey 密钥格式对不对（kid:key，32 位十六进制）

起播慢

  • 先看「DASH 调优 → 播放体验 → 快速起播窗口」，但改之前记住默认值适配大多数源
  • 检查上游 CDN 延迟

卡顿

  • 先确认出口带宽跑满没有
  • 再看「抗卡缓冲」和「磁盘最少保留」
  • 并发下载别设太高，频道多时会打满连接

字幕不显示 / 样式不对

  • 字幕设置只对 DASH 频道生效，确认分组模式没选错

内存占用高

  • 「整片内存预算」保持自动（0），或手动封顶到 128MB
  • 「发片方式」改用流式

工作模式 · 302 跳转（Redirect）

模式标识：redirect　|　面板位置：分组管理 → 编辑分组 → 工作模式

一句话：你的服务器不下发内容，只回一个 302，让播放器自己去源站拉流。流量不经过你。

面板的官方说明：「客户端按 302 直连上游,本服务仅做调度。带宽零开销,但客户端会暴露上游地址。」

数据怎么流

播放器  ──请求──▶  IPTV Proxy  ──302──▶  源站地址
   ▲                    │
   └────播放器直接去源站拉流────┘

✅ 你的服务器只出了一次 302，之后完全不承载流量

使用条件

场景说明
省带宽流量直连源站，你的服务器只处理请求
源站稳定不需要代理层的容错
源是 FLV / 直链源面板的 M3U 导入里，Redirect 明确标注适合这类源
源靠 IP 白名单玩家的出口 IP 直连源站，注意得放得下

不适用场景

  • 需要隐藏源地址 → 302 会把源站地址明明白白交出去，用 Proxy
  • 需要缓存加速 → Redirect 不缓存
  • 需要本地回看 / 录制 → Redirect 不经过本地拉流，没有切片
  • 源站限制单 IP 并发 → 每人从自己的 IP 直连，源站并发压力上升

本模式的全部配置项

通用字段见 通用配置项详解。Redirect 独有的是跳转方式和上游缓存时长两项。

分组级

字段什么时候填例子
工作模式固定选「Redirect（302 跳转）」—
跳转方式决定跳转前做多少准备工作，见下方详解绝大多数情况选「直接跳转」
上游缓存时长解析出来的上游地址缓存多少秒源地址带时效 token → 填比 token 有效期短的值

跳转方式（Redirect 独有）

选项它做了什么什么时候选
直接跳转（默认）真正意义的 302：脚本频道零回源直接跳；静态地址只跟随重定向拿落地地址，不下载播放列表上游本来就是成品地址（绝大多数情况），换台更快
解析最佳画质多下一次播放列表。若上游给的是 master 清单，就替客户端挑码率最高的那一路再跳上游给的是多码率 master，你想让用户固定看最高画质

建议先用默认的「直接跳转」。只有当你发现用户播到的是低码率、且上游确实是 master 清单时，才改成「解析最佳画质」。后者每次跳转要多一次回源。

上游缓存时长

缓存的是「解析出来的上游地址」，不是媒体切片。

关键：带时效 token 的源，这里要填得比 token 有效期短。 例子：源地址里的签名 300 秒就失效 → 上游缓存时长填 240，留 60 秒余量。填太长会拿到已过期的地址，表现为「过一会儿就开始 403」。

默认值是 300 秒（面板的输入框占位符）。

网络配置（分组级）

Redirect 分组会显示完整的网络配置，和 Proxy 一样：

字段什么时候填例子
User-Agent源报 403 或返回错误页时Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/120.0
代理类型 / 地址 / 用户名 / 密码想隐藏服务器 IP 时127.0.0.1:7890
自定义请求头源要 Referer 才放行时Referer: https://example.com/

这里有个反直觉的地方：Redirect 的 302 响应不经过你的服务器转发媒体，但「跟随重定向拿落地地址」这一步会用到你设的 UA 和请求头。所以这两个字段在 Redirect 下仍然有用。

频道级

Redirect 不经过本地拉流，所以没有推流 / 回看区块。取而代之的是源站回看：

字段什么时候填例子
上游支持回看源站自己能处理回看才选「是」，程序只把 playseek 追加到上游 URL源站支持时选「是」
回看天数源站能回看多少天。填大了播放器会拖到没有内容的时段源站支持 7 天 → 填 7

回看能力来自源站，不是你的服务器。 这是 Redirect / Rewrite / Passthrough 三种模式共有的特点。

不会出现的字段

字段为什么没有
回看保留时长 / 最大磁盘占用 / 时间偏移不录本地切片
预载配置只有 Proxy 有
ClearKey 密钥那是 DASH 用的
MPD 裁剪保留秒数只有 (Proxy 或 Rewrite) 且格式=MPD 时才出现
源容器类型那是 Remux 用的

配置步骤

  • 分组管理 → 新建分组 → 工作模式选 Redirect（302 跳转）
  • 跳转方式选直接跳转（默认）
  • 上游缓存时长：源地址不带时效 token 就用默认 300；带 token 就填短一点
  • 新建频道，填上游 URL、频道 ID、tvg-id
  • 需要回看就开「上游支持回看」并填回看天数
  • 复制订阅地址，导入播放器

代价

  • 你的出网带宽 ≈ 0，这是它最大的价值
  • 服务器只承担 302 响应，CPU 和内存占用都可以忽略
  • 源站的并发压力由观众承担。 观众集中访问同一源时，源站可能返回限流响应

排错

播放器拿到订阅但播不了

  • 播放器是否支持 302 跟随？部分电视端播放器对跳转链支持不好
  • 试试换成 Proxy 看是不是播放器的问题

跳过去了但源站拒绝

  • 源站可能按 IP 鉴权或限制地域。Redirect 让播放器用自己的出口 IP 直连。服务器上的 UA 和 Referer 只作用于获取落地地址这一步，不影响后续的拉流请求
  • 这是切 Redirect 最常见的翻车点

刚开机能播，过一会儿开始 403

  • 上游缓存时长填太长，缓存了已过期的地址。调短它

想改跳转目标 / 加鉴权

  • Redirect 模式本身不适合加鉴权，那需要 Proxy

工作模式 · URL 改写（Rewrite）

模式标识：rewrite　|　面板位置：分组管理 → 编辑分组 → 工作模式

一句话：只把 M3U8 播放列表里的相对地址改成绝对地址，不转发任何内容。最轻的一种模式。

面板的官方说明：「改写 M3U8/MPD 中的 URL 为绝对地址,切片由客户端直连上游。轻量代理。」

数据怎么流

播放器  ──请求──▶  IPTV Proxy  ──返回改写后的播放列表──▶  源站（只取一次清单）
   ▲                    │
   └────播放器自己去源站取切片────┘

✅ 切片不走你的服务器

服务器只做一件事：拿到 .m3u8 清单，把里面 /live/seg1.ts 这类相对路径改成 http://源站/live/seg1.ts，然后把清单交给播放器。之后的切片流量完全在播放器和源站之间。

使用条件

场景说明
源的清单用了相对路径直接喂播放器会解析失败，改写成绝对地址就能播
需要极轻量的整理服务器只出流量，不承载媒体
频道数量很多但流量分散每个频道各拉各的，你的带宽压力小
M3U 批量导入的默认落点导入时「自动识别」把非 .mpd 的频道都归到这里

不适用场景

  • 需要隐藏源地址 → 改写后源站地址明明白白写在清单里
  • 需要缓存 → Rewrite 不缓存，每次播放都重新拉
  • 源站限制单 IP 并发 → 每个人都从自己的 IP 直连
  • 需要本地回看 / 录制 → 不经过本地拉流

M3U 导入的默认策略就是 Rewrite：面板标注「Rewrite - 改写 M3U8 为绝对地址(HLS 通用)」。这是安全的默认值——不代理、不消耗带宽，先保证能播。

本模式的全部配置项

通用字段见 通用配置项详解。Rewrite 的专属字段很少。

分组级

字段什么时候填例子
工作模式固定选「Rewrite（URL 改写）」—
内容格式上游给的是 .m3u8 还是 .mpd源是 .m3u8 → HLS
MPD 裁剪保留秒数只在「内容格式 = MPEG-DASH」时出现30

内容格式选 MPD 时会怎样

面板代码里对三种模式 + MPD 的组合有明确区分：

模式 + 内容格式实际行为
Proxy + MPD反代穿透本服务
Rewrite + MPD直连 CDN
Redirect + MPD直连 CDN

也就是说，Rewrite 和 Redirect 选 MPD 时并不转封装，只是把 MPD 地址原样给出去。如果你真的需要 MPD→HLS 的转换，用 DASH 模式。

网络配置

Rewrite 分组会显示完整的网络配置（和 Proxy / Redirect 一样）：

字段什么时候填例子
User-Agent取清单时被 403 就填Mozilla/5.0 ... Chrome/120.0
代理类型 / 地址 / 用户名 / 密码想隐藏服务器 IP 时127.0.0.1:7890
自定义请求头源要 Referer 才给清单时Referer: https://example.com/

重要：Rewrite 下你的服务器只负责取清单，请求头设置在这一步生效。播放器之后自己取切片，那部分不受你的设置影响——所以源站要求 Referer 才能取切片时，Rewrite 会失败，得换 Proxy。

频道级

Rewrite 不经过本地拉流，所以没有推流 / 回看区块。取而代之的是源站回看：

字段什么时候填例子
上游支持回看源站自己能处理回看才选「是」源站支持时选「是」
回看天数源站能回看多少天。填大了播放器会拖到没有内容的时段7

不会出现的字段

字段为什么没有
回看保留时长 / 最大磁盘占用 / 时间偏移不录本地切片
上游缓存时长、跳转方式那是 Redirect 独有的
源容器类型那是 Remux 独有的
预载配置只有 Proxy 有
ClearKey 密钥那是 DASH 用的

与 Redirect 的区别

两个都是「流量不走服务器」，区别在于服务器出了多少力：

RewriteRedirect
服务器做什么取清单、改写相对地址回一个 302
清单谁去取你的服务器取一次播放器自己去取
适合源清单用了相对路径的 HLS任意直链、.flv、.ts
带宽极小（只有清单）极小（只有 302）

简单判断：源的 .m3u8 里写的是相对路径 → Rewrite；源本身要给直链（.flv、.ts）→ Redirect。

配置步骤

  • 分组管理 → 新建分组 → 工作模式选 Rewrite（URL 改写）
  • 新建频道，填上游 URL、频道 ID、tvg-id
  • 需要回看就开「上游支持回看」并填回看天数
  • 复制订阅地址，导入播放器

导入场景下大多数分组不需要手改——M3U 导入会自动把非 .mpd 的频道放进 Rewrite 分组。

代价

  • 带宽接近零，服务器只承担清单请求
  • CPU 和内存占用都极低
  • 但你放弃了全部控制：没有缓存、没有隐藏、没有录制、无法鉴权

排错

改写后还是播不了

  • 打开源站的 .m3u8 看一眼：如果它本来就是绝对地址，Rewrite 没有可改写的东西，问题在源站或播放器
  • 源是不是加密的？Rewrite 不处理加密，那种情况需要 DASH 或 Proxy

清单能取到但切片 404

  • 源站可能校验 Referer。Rewrite 的请求头只作用于获取清单。 播放器获取切片时不携带该设置。此类源站需要改用 Proxy

想改策略但怕破坏现有分组

  • 切换模式前先在「分组管理」用导出全部备份，模式切换后如果有问题可以导回

工作模式 · 直链（Passthrough）

模式标识：passthrough　|　面板位置：分组管理 → 编辑分组 → 工作模式

一句话：不代理、不改写、不加 token，原样把上游 URL 交给播放器。服务器只负责记账。

面板的官方说明：「原样导出别人的 URL,不经本服务;有 ClearKey 则按 MPD。」

数据怎么流

播放器  ──请求──▶  IPTV Proxy
   ▲                    │
   │    返回的就是上游原始地址
   └────────────────────┘

✅ 订阅里写的地址 = 上游地址

与其他模式最大的区别：Passthrough 的播放地址直接就是上游 URL，不走 /{分组}/{频道} 这套路由。

使用条件

场景说明
完全信任的源你的官方源、自己的 CDN
只想统一管理频道清单让这些频道出现在总订阅里，但流量完全不参与
源本身就是公开直链没有鉴权、没有加密、没有必要代理
给订阅做一个占位条目频道存在，但由别的途径播放

不适用场景

任何需要控制的情况都不要用：

  • 需要隐藏源地址 → Passthrough 是把地址直接交出去
  • 需要 Token 防盗链 → Passthrough 不加 token，这是它字面意思的一部分
  • 需要缓存 / 回看 / 录制 → 都不经过本地拉流
  • 源有鉴权或加密 → 完全暴露

它是唯一一个默认不套用 Token 的模式。别在需要防盗链的分组里用。

字段什么时候填例子
工作模式固定选「Passthrough（直链）」—
内容格式 / 预载切片上限不显示——直链不选格式，也不需要预载
网络配置（UA / 代理 / 请求头）会显示

为什么 Passthrough 会有 ClearKey 密钥区

面板代码里写得很直白：

直链（有 key 即按 MPD 下发）也显示

例子：源是加密的 MPD，你在 Passthrough 频道里填上密钥，订阅里的地址就会带上对应的解密信息。

但要注意：Passthrough 不做任何解密动作，它只是把密钥信息附在地址里。能不能解开取决于播放器自己。

上游缓存时长、跳转方式那是 Redirect 用的

配置步骤

  • 分组管理 → 新建分组 → 工作模式选 Passthrough（直链）
  • 新建频道，上游 URL 填完整的直链地址
  • tvg-id 照常填，EPG 匹配要用
  • 源加密的话填上 ClearKey 密钥
  • 保存后复制订阅地址

这个模式下上游 URL 是唯一的关键字段——它会原样出现在播放器里。

代价

  • 带宽、CPU、内存占用全部为零——服务器只存了一条记录
  • 但相应地：无法统计真实观看情况之外的东西，也不提供任何转发价值

频道热度统计仍会记录播放列表的请求，这是 IP 管控和热度统计的监控对象。

排错

订阅里的地址变成了上游原始地址

  • 这是设计如此，不是 bug。Passthrough 的播放地址就是上游 URL

加了 token 但还是被外链盗用

  • Passthrough 不套用 Token。要防盗链必须用 Proxy 配合 Token + 随机频道 ID

源是加密的放不了

  • Passthrough 不做任何解密。加密源需要 DASH（ClearKey）或 Proxy

这个分组在总订阅里看不到

  • 检查分组的「访问范围」是不是设成了隐藏（不进总订阅）

通用配置项详解

六种工作模式共用的字段。理解了这里，换任何模式都不用再学一遍。 各模式的专属字段见对应的模式指南。

一、分组级字段

在 分组管理 → 编辑分组 里。分组是一批频道的容器，决定订阅地址长什么样。

分组 ID

这个字段决定了你的订阅地址，起名要慎重。

项说明
规则只用小写字母、数字和短横线 -
作用出现在 http://你的IP:19899/<分组ID>/playlist.m3u 里
后果改了会让已分发出去的地址全部失效

例子：填 cctv，订阅地址就是

http://192.168.1.10:19899/cctv/playlist.m3u

建议：用英文小写、能看出内容的短词。不要用中文（部分播放器对非 ASCII 的 URL 兼容性差），不要用空格。

显示名称

写进 M3U 的 group-title，是播放器里显示的分类名。改它不影响地址，随便改。

例子：分组 ID 填 cctv，显示名称填「央视套」，播放器的分组列表里就显示「央视套」。

工作模式

六选一，决定这组频道怎么转发。这是本手册 mode-*.md 讲的内容。

模式一句话
Proxy（反向代理）全面，最通用，默认选它
Remux（连续流 → HLS）源是 FLV/TS/MMT 时用
Redirect（302 跳转）最省你的带宽
Rewrite（URL 改写）M3U 导入的默认落点
DASH（MPD → HLS）源是 .mpd 或带 ClearKey
Passthrough（直链）完全信任的源，不加 token

EPG 地址

写进 M3U 头部的 x-tvg-url，告诉播放器去哪取节目单。

填法效果
点下方按钮填 /epg.xml.gz用本机 EPG 页生成的那份（推荐）
留空播放器拿不到节目单
填外部地址用第三方的节目单

例子：/epg.xml.gz

前提是 EPG 总开关已打开。关掉的话这个地址返回 404，播放器那边就是「有节目单地址但拉不到内容」。

访问范围

选项行为什么时候用
公开正常出现在总订阅里绝大多数分组
隐藏直接访问地址能播，但不进总订阅想分享给特定人、又不出现在大订阅里
归档整组停用，但 EPG 与台标匹配照常暂时下架的频道，保留节目单
免验证不校验 token 的公开入口想做免登录的免费入口

例子：你有一个分组只想给朋友，给它设「隐藏」——朋友直接拿地址能播，但别人翻总订阅看不到这一组。

网络配置（分组级）

这组字段在六种模式下都会显示。 面板只对 5 个特定字段做了模式区分（上游缓存时长、跳转方式、源容器类型、内容格式、MPD 裁剪保留秒数），网络配置不在其中。

User-Agent

回源时用的 UA，部分源站按 UA 放行。留空用程序默认值。

什么时候必须填：源站报 403、或者直接给你返回一段错误页的时候，八成是 UA 被拦了。

例子：

Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0 Safari/537.36

代理类型

选项说明
不使用代理直连回源（默认）
HTTP 代理host:port 形式的 HTTP 代理
SOCKS5SOCKS5 代理，DNS 走本地
SOCKS5HSOCKS5 代理，DNS 也走代理

选哪个：想隐藏服务器 IP 就填。访问国内源却要绕到境外才选 SOCKS5H。

代理地址 / 代理用户名 / 代理密码

地址填 host:port，不带协议前缀。代理类型选「不使用代理」时不生效。

例子：127.0.0.1:7890 或 proxy.example.com:1080

自定义请求头

回源时附加的请求头，常用 Referer、Host、Cookie。User-Agent 请用上面那个独立输入框，两处都设会打架。

例子（每行一条）：

Referer: https://example.com/
Origin: https://example.com

这是排查「能播但很卡」和「直接 403」的常用武器。部分源站要求 Referer 匹配，不填就被拒。

二、频道级字段

在 分组管理 → 编辑频道 里。

频道 ID

决定播放地址。同一分组内不能重复，改了旧地址立即失效。

例子：分组 cctv 下的频道 cctv1，播放地址是

http://192.168.1.10:19899/cctv/cctv1.m3u8

频道名称

播放器列表里显示的名字，EPG 自动匹配也会拿它比对。随便改，不影响地址。

例子：CCTV-1 综合

上游 URL

真正的源地址。

例子：

http://live.example.com/hls/cctv1.m3u8      ← HLS，Proxy/Rewrite/Redirect 常用
http://live.example.com/live/cctv1.flv      ← FLV 连续流，Remux 用
http://live.example.com/dash/cctv1.mpd      ← MPEG-DASH，DASH 模式用

上游类型选了「脚本解析」时可以留空——地址由脚本每次播放前算出来。

频道 Logo URL

台标地址。留空则用「台标管理」里匹配到的本地台标。

例子：https://example.com/logo/cctv1.png

别填外链图床。填了图标每刷新都要去别人的服务器要一次，很容易被限速或挂掉。用「台标管理」把图存本地，面板会自动帮你填好。

tvg-id

EPG 匹配用的标识，必须和节目单里的频道 id 一致。留空则用频道 ID。

例子：节目单里的 id 是 CCTV1.com，这里就填 CCTV1.com。

这是 EPG 匹配失败最常见的原因。频道能播但节目单是空的，八成就是这里没填对。 填完到「节目指南 → 频道匹配」看报告，「未匹配」的数量应该会降下来。

tvg-name

EPG 匹配的备用名，留空则用频道名称。tvg-id 对不上时还会拿它再试一次。

例子：CCTV-1 综合

上游解析

选项说明
静态 URL直接用上面填的地址（绝大多数情况）
脚本解析（PY）每次播放前跑一段 Python 算出地址

什么时候用脚本解析：源站的地址带时效签名（每次请求的 URL 里都有不同的 token，过几分钟就失效）。这种源没法把地址写死，得让脚本每次去算。

脚本解析需要系统装了 python3。

解析脚本 / 脚本参数 / 解析缓存时长

选了「脚本解析」才出现。

  • 解析脚本：选一个已上传的 .py，脚本要返回一个可直接播放的地址
  • 脚本参数：传给脚本的 ID 或参数，具体填什么取决于脚本自己的约定
  • 解析缓存时长：脚本算出的地址缓存多少秒，留空继承分组

例子：脚本参数填 channel_id=cctv1

解析缓存时长要小于源站签名 token 的有效期。比如签名 5 分钟就失效，缓存填 300 秒刚好卡在边界，建议填短一点（240）留余量。

三、频道级的通用网络配置

和分组级同名，但频道级优先：分组和频道都填了，以频道级的为准；请求头则是合并，同名以频道级为准。

  • User-Agent：留空则继承分组设置
  • 代理类型：留空 / 选「继承分组设置」则用分组的
  • 代理地址 / 用户名 / 密码：同上
  • 自定义请求头：与分组级合并，同名以频道级为准

例子：分组里统一设了 UA，但某个源特别严格，在那个频道里单独填它要求的 UA。

三个反直觉的结论

1. 决定 CPU 的是码率，不是人数

CPU 花在转发字节上。1 个用户看 4K（20 Mbps）比 5 个用户看 720p（2 Mbps）更费 CPU。

换算方式（以 1080p / 6.2 Mbps 为基准 1.0）：

码率倍数
4K / 20 Mbps×3.2
1080p / 6.2 Mbps×1.0
720p / 2 Mbps×0.3
480p / 1 Mbps×0.16

2. 同一频道多人 ≈ 比一个人还省

5 个人看同一个频道时 CPU 只要 0.51% 单核，比 1 个观众的 0.86% 还低。

原因是切片缓存共享：回源只发生一次，5 个观众共用同一份切片。回源流量从 5.8 MB/s 降到 3.9 MB/s，CPU 减半。

推论：观众扎堆看同一个频道（比如都在看春晚）几乎不增加成本，人分散看不同频道才贵。

3. 冷缓存才是直播的真实成本

实测里「1 个观众」比「5 人同一频道」还费 CPU，因为那一档是冷缓存（首次回源 + 解析清单）。

而直播场景永远接近冷缓存——每个切片只出现一次，播完即弃。

所以估算直播服务器容量时，要用冷缓存那档的数字，不要用缓存命中的。

真正的瓶颈是带宽

10 个观众看 6.2 Mbps 直播 = 62 Mbps 出网。这比 CPU 重要一个数量级——CPU 才 0.4% 单核，带宽却要 62 Mbps。

判断方法：看面板「在线观众」。十来个人的小圈子用整片；几十上百人同时看就用流式。

整片内存预算默认是「可用内存的 1/8，封顶 512 MB」，小内存机器会自动调低。

怎么自己测

面板「概览」页有实时指标，但面板的回源流量统计在 v0.8.2 里失效（累计回源一直显示 0，而实际在回源）。要用容器层的数据：

# 看容器 CPU / 内存 / 网络
docker stats --no-stream --format '{{.CPUPerc}}  {{.MemUsage}}  {{.NetIO}}' iptv

CPUPerc 以单核 100% 为基准（所以 10% 表示用了 0.1 个核）。NetIO 是累计值，两次采样取差值就是速率。

测的时候注意：

  • 先在面板建好频道，确认能正常播放
  • 用多个播放器或脚本持续拉取该频道的播放地址
  • 间隔 20 秒以上采样两次，算差值
  • 区分冷/热缓存：播过一次之后再测是热缓存；换新频道或清空缓存是冷缓存

面板内的实时指标仍可用于看 CPU 累计秒数和内存（这两个是准的），只有回源流量不准。

测试局限

说清楚这份数据的适用范围：

  • 用的是 VOD 点播流，不是真直播。切片长度与刷新节奏和直播有差异
  • 用 curl 模拟拉取，不是真实播放器（不发 Range 请求、不做缓冲策略）
  • macOS 上测的，Linux VPS 的 CPU 绝对值会有差异，但相对关系（人数 vs 码率 vs 缓存）可用
  • 实测回源流量为 3–13 MB/s，高于真实直播场景。原因是该测试的缓存命中率偏低。因此内存数值偏保守
  • 未开启 Token、预载、录制、EPG 等功能。开启后会增加占用

结论适用于「中低并发 + 单一代理模式」的容量规划。 高并发（百人以上）或叠了录制、预载时，请以自己面板的实测读数为准。

切片伪装的实现方式

本文记录 IPTV Proxy v0.8.2 的实测结果。测试在 localhost:19899 上进行。样本是面板自带的 test 分组。

每条结论都附验证方法。你可以逐条复现。

⚠️ 本文分析的是面板自带的测试源。第三方直播源的实现可能不同。

采集日期：2026-10-03。

结论

切片伪装不修改切片内容。 程序只改写 URL 后缀和 Content-Type。切片的每一个字节都保持原样。

伪装发生在四层。四层都不改变载荷。

层值是否改变字节
URL 后缀png jpg gif bmp webp否
Content-Typeimage/png image/jpeg image/webp image/bmp否
路径形状清单写成 .txt，切片平铺在频道目录下否
切片载荷原始 MPEG-TS，188 字节一个包否

切片不是图片。程序也没有把切片编码进图片。 这一点与多数人的预期相反。

一、地址链路

从订阅地址到切片，一共经过三层 HTTP 请求。

http://localhost:19899/playlist.m3u8
  └─ 第 1 条 T1
     └─ http://localhost:19899/test/t1.m3u8?token=29c6b95a...
        │  Content-Type: application/vnd.apple.mpegurl
        │  这是一份主清单（master）
        └─ http://localhost:19899/test/t1/video/index.txt
           │  Content-Type: text/plain; charset=utf-8
           │  这是一份媒体清单（media），伪装成了 .txt
           └─ http://localhost:19899/test/t1/0d9ec19b3b78ba7b_18e34bfbb515537d2bc7054e33d8ecfc.png
              Content-Type: image/png
              这是一段原始 MPEG-TS

注意主清单的地址没有被伪装。/test/t1.m3u8 仍以 .m3u8 结尾。

「主列表伪装」开关控制的不是这一层。

字段值

五、缓存窗口

这是伪装的真正目的。

Cache-Control 不是固定值。

时机响应头
切片刚写入缓存cache-control: public, max-age=300
之后cache-control: private, max-age=300

实测记录。

public, private, private, private, private, private   ← 全新切片连打 6 次

窗口很短，且随时间变化。它不是固定的请求次数。

公开窗口让 CDN 按图片规则收下这个对象。随后的 private 让 CDN 不再存储它。

这样 CDN 命中一次真实用户的取片，之后的匿名重复请求不计入 CDN 的滥用统计。

没有 CDN 时，这层收益不存在。详见 面板与运维参考 的「前置条件」。

项实测值

Range 请求忽略。返回 200 和完整内容

不支持 Range 会影响按需起播的部分播放器。

切片伪装

把切片伪装成图片，借 Cloudflare 默认图片缓存规则命中 CDN，降低被滥用报告的风险。

它和反向代理是绑定的：只有流量真正经过你的服务器时，程序才能把切片地址改写成图片后缀。 所以它只对代理类模式有意义——Proxy、Remux、DASH。 Rewrite / Redirect / Passthrough 的切片是上游直连的，改不了；订阅聚合来的频道更是完全不经过本服务。

选项说明建议
切片伪装把切片地址伪装成图片后缀，借 CDN 图片缓存规则提高命中率前面有 CDN 时开
列表伪装把 .m3u8 / .mpd 也伪装成图片。面板说明：列表刷新频繁，收益大于切片伪装开启
字幕 .vtt 伪装字幕体积小，收益有限，个别播放器会解析失败关闭（面板标注推荐）
主列表伪装只影响多码率的 master 列表。部分 iOS 播放器认不出伪装后的 master关闭（面板标注推荐）
伪装格式jpg / png / gif / bmp / webp，多选，按切片稳定轮换至少勾两个
实测结果（v0.8.2，单码率 + 多码率两种源对比）

配置项在 config.toml 的 [cache.disguise] 段：

[cache.disguise]
enabled  = true                        # 切片伪装总开关
playlist = true                        # 列表伪装
subtitle = false                       # 字幕 .vtt 伪装
master   = false                       # 主列表伪装
formats  = ["jpg","png","gif","bmp","webp"]

出厂默认就是 enabled = true + playlist = true，不用手动开。

实测三层地址的变化（单码率源）：

层伪装关闭伪装开启
播放入口（订阅里那条）http://host/组/频道.m3u8http://host/组/频道.m3u8 ← 不变
清单里的切片..._18e34b....ts..._18e34b....webp / .png / .jpg ← 变

结论与常见误解相反：

  • ✅ 切片后缀确实被改写，在勾选的图片格式间轮换（实测依次出现 .webp → .png → .jpg）
  • ❌ 播放入口地址永远是 .m3u8，不因开启伪装而改变。分发出去的订阅地址不会失效，不需要重新发地址
  • ⚠️ 面板源码注释里「入口地址要带扩展名（.m3u8 / .mpd / 伪装时 .txt）」中的 .txt 分支，

    在实测中只出现在多码率 master 的子流地址上（.../video/index.txt），那是程序对多码率源做规范化 转封装后自己生成的路径，不是伪装开关的效果——把它关掉，该地址依然是 .txt

补充观察：

  • playlist / master / subtitle 三个开关在本次实测（单码率源 + 多码率源）中没有观察到任何地址变化，

    本次实测未观察到这三个开关对地址的影响。实测生效的设置是总开关 enabled

  • 文件名混淆（..._18e34bfbb515537d2bc7054e33d8ecfc）与伪装无关，由 cache.dash.obfuscate_filenames 独立控制
伪装到底改了什么（字节级结论）

切片伪装不修改切片内容。 程序只改写 URL 后缀和 Content-Type。

下载四种后缀的同一切片，前 32 字节逐字节相同。首字节是 0x47，这是 MPEG-TS 的同步字节。

每 188 字节都是 0x47。文件大小是 188 的整数倍。文件里没有 JPEG、PNG、WebP、BMP 或 fMP4 的特征字节。

把 .png 改名成 .ts，ffprobe 直接识别为 MPEG-TS，1920x1080 H.264 + AAC。

层值是否改变字节
URL 后缀png jpg gif bmp webp否
Content-Typeimage/png image/jpeg 等否
路径形状清单写成 .txt，切片平铺在频道目录下否
切片载荷原始 MPEG-TS，188 字节一个包否

另外三个实测结论：

  • 后缀不参与校验。 清单写 .png 时，你请求 .jpg 也能拿到同一份字节，MD5 相同
  • 轮换稳定且按频道独立。 同一频道重复拉清单，扩展名序列不变；同一切片哈希在不同频道拿到不同后缀
  • Cache-Control 会切换。 切片刚写入缓存时短暂返回 public, max-age=300，之后长期返回 private, max-age=300。公开窗口让 CDN 按图片规则收下对象，随后的 private 让 CDN 不再存储它。这层收益需要 CDN

切片还带有两项特征：

  • 每个切片是自包含的 MPEG-TS，自带 PAT / PMT / SDT 和约 10 秒媒体
  • 每个切片的第 0 个包携带 SDT，其描述符载荷是字符串 lumberjack（两次）。这是来源水印，与伪装无关

完整验证步骤、字节证据、扩展名分布表和 PID 表见 切片伪装的实现方式。

怎么用
  • 默认就已经开着，直接用即可
  • 要调整：系统设置 → 切片伪装 → 改开关与格式 → 保存
  • 切换伪装总开关会改变切片 URL。已缓存切片的播放器需要重新加载播放列表
  • 播放入口地址不受影响，分发出去的订阅继续有效
前置条件

伪装的效果来自 CDN 对图片类文件的缓存规则。没有 CDN 时收益很有限——直连场景下程序改后缀也换不来缓存命中。

⏰ 定时录制

为 Proxy / DASH 频道设置定时录制任务。

运行机制：

  • 到达开始时间后系统自动启动该频道的流并录制，无需提前手动开启推流或回看
  • 录制结束自动停止：若期间无人观看且频道非常驻，录制结束即回收；若有人观看或为常驻频道，保持运行
  • 开始时间设为过去时，会尝试从已保留的回看历史补录
  • 录制完成后切片自动合并为 MKV。支持多音轨。中断后仍可播放

⚠️ 必须安装 ffmpeg，否则录制任务直接失败（用于封装 MKV，不转码）。 支持 Proxy（HLS，含多音轨/多字幕）和 DASH 两种模式频道。文件保存在 cache/recordings/。

安装：apt install ffmpeg · brew install ffmpeg · Windows 下载后加入 PATH。

配置文件

面板里改的设置最终都写入 /opt/iptv-proxy/config.toml。文件只写最小必要项，其余走内置默认值——在面板改任何设置并保存后，后端会把完整配置回写。

[server]
bind = "[::]:19899"          # [::] 双栈；只要 IPv4 写 0.0.0.0:PORT
timezone_offset_hours = 8    # 中国大陆填 8，影响回看/EPG 时间
log_level = "info"           # trace / debug / info / warn / error

[panel]
enabled         = true
username        = "admin"
password_sha256 = "..."      # SHA-256，明文不落盘
session_ttl     = 86400      # 会话有效期（秒），默认 24 小时

[cache]
backend             = "disk"
disk_path           = "./cache"
m3u8_max_entries    = 500
segment_max_entries = 2000
disk_max_mb         = 0      # 0 = 不限

[auth]
token_enabled = false        # 建议公网部署时改为 true

配置文件有热重载监视，直接改文件也能生效（前提是热重载未被关闭）。

Docker 部署（本环境）

本环境以容器方式运行，服务由容器内的启动脚本拉起：

容器名：iptv        镜像：alpine/curl:latest
