# 资源占用实测

> 本文是 **v0.8.2 的实机测量结果**，不是估算。数据来自本地容器实测，方法和局限写在文末。

---

## 测试环境

| 项 | 值 |
| --- | --- |
| 程序 | IPTV Proxy v0.8.2 |
| 部署 | Docker 容器（`alpine/curl`，无挂载卷） |
| 机器 | macOS，10 核 / 15.7 GB |
| 频道源 | Mux 公开测试流，1080p HLS，约 **6.2 Mbps** |
| 缓存后端 | `disk` |
| 切片伪装 | 开启（默认） |
| Token | 关闭 |

测量方式：模拟播放器持续拉取播放列表与切片，从容器层（`docker stats`）和面板 `/status/metrics` 两边取数。

---

## 实测数据

### 三个档位

| 并发观众 | CPU（占单核） | 容器内存 |
| --- | --- | --- |
| **1 个** | **0.86%** | **71 MB** |
| **2 个**（不同频道） | **1.31%** | **77 MB** |
| **5 个**（不同频道） | **1.07 – 1.51%** | **89 – 117 MB** |

### 完整对照

| 场景 | CPU（占单核） | 容器内存 | 回源 | 出网 |
| --- | --- | --- | --- | --- |
| 空闲 | ~0% | 28 MB | — | — |
| 1 观众（冷缓存） | 0.86% | 71 MB | 7.3 MB/s | 0.3 MB/s |
| 1 观众（热缓存） | 1.06% | 90 MB | 8.8 MB/s | 2.0 MB/s |
| 2 观众（不同频道） | 1.31% | 77 MB | 9.7 MB/s | 3.4 MB/s |
| 5 观众（**同一频道**） | **0.51%** | 78 MB | 3.9 MB/s | 3.1 MB/s |
| 5 观众（**不同频道**） | 1.07 – 1.51% | 89 – 117 MB | 5.8 – 13.1 MB/s | 3.5 – 4.2 MB/s |

---

## 三个反直觉的结论

### 1. 决定 CPU 的是码率，不是人数

CPU 花在转发字节上。**1 个用户看 4K（20 Mbps）比 5 个用户看 720p（2 Mbps）更费 CPU。**

换算方式（以 1080p / 6.2 Mbps 为基准 1.0）：

| 码率 | 倍数 |
| --- | --- |
| 4K / 20 Mbps | ×3.2 |
| 1080p / 6.2 Mbps | ×1.0 |
| 720p / 2 Mbps | ×0.3 |
| 480p / 1 Mbps | ×0.16 |

### 2. 同一频道多人 ≈ 比一个人还省

5 个人看**同一个频道**时 CPU 只要 **0.51% 单核**，比 1 个观众的 0.86% 还低。

原因是**切片缓存共享**：回源只发生一次，5 个观众共用同一份切片。回源流量从 5.8 MB/s 降到 3.9 MB/s，CPU 减半。

> 推论：观众扎堆看同一个频道（比如都在看春晚）几乎不增加成本，人分散看不同频道才贵。

### 3. 冷缓存才是直播的真实成本

实测里「1 个观众」比「5 人同一频道」还费 CPU，因为那一档是**冷缓存**（首次回源 + 解析清单）。

而直播场景**永远接近冷缓存**——每个切片只出现一次，播完即弃。

**所以估算直播服务器容量时，要用冷缓存那档的数字，不要用缓存命中的。**

## 换算到你的 VPS

CPU 按**单核百分比**换算，再乘码率倍数：

| 并发观众 | CPU 需求 | 内存需求 | 最低配置 | 建议配置 |
| --- | --- | --- | --- | --- |
| 1 – 5 | 0.1 – 0.15 核 | 70 – 120 MB | 1 核 / 512 MB | 1 核 / 1 GB |
| 10 – 20 | 0.2 – 0.4 核 | 200 – 400 MB | 1 核 / 1 GB | 2 核 / 2 GB |
| 50 | 0.8 – 1.5 核 | 约 1 GB | 2 核 / 1 GB | 2 核 / 2 GB |
| 100+ | 1.5 – 3 核 | 需限缓存 | 4 核 / 2 GB | 4 核 / 4 GB |

> ⚠️ **只有前三行是实测**。10 / 50 / 100 是外推，模型是：CPU 随总码率线性、随人数略次线性；内存每观众约 15–22 MB（由 28 MB → 117 MB 推得）。
> 实际以你自己的面板读数为准。

---

## 真正的瓶颈是带宽

10 个观众看 6.2 Mbps 直播 = **62 Mbps 出网**。这比 CPU 重要一个数量级——CPU 才 0.4% 单核，带宽却要 62 Mbps。

控制成本优先看带宽，不是 CPU：

| 手段 | 效果 | 代价 |
| --- | --- | --- |
| **切 [Rewrite](mode-rewrite.md) 模式** | 出网归零 | 无缓存、无 Token、无回看 |
| **切 [Redirect](mode-redirect.md) 模式** | 出网归零 | 暴露源地址 |
| 降低码率 | CPU 和带宽同步下降 | 画质 |
| 用 [Remux](mode-remux.md) 替代 Proxy | CPU 更低 | 仅源为连续流时适用 |

---

## 把内存压住

内存增长主要来自缓存。实测每观众约 15–22 MB，两个开关能控制：

| 位置 | 配置 | 效果 |
| --- | --- | --- |
| 系统设置 → 缓存配置 | `内存上限` | 内存缓存的硬上限，设了就不会无限涨 |
| 系统设置 → DASH 调优 → 特殊场景 | **发片方式** | 见下 |

### 发片方式：整片 vs 流式

| 选项 | 每连接内存 | 适合 |
| --- | --- | --- |
| **整片** | 1 – 2 MB | 带宽大、人不多。高带宽高延迟链路上更顶满发送窗口 |
| **流式** | **64 KB** | **人多或内存紧**。内存与观看人数几乎无关 |

**判断方法**：看面板「在线观众」。十来个人的小圈子用整片；几十上百人同时看就用流式。

整片内存预算默认是「可用内存的 1/8，封顶 512 MB」，小内存机器会自动调低。

## 怎么自己测

面板「概览」页有实时指标，但**面板的回源流量统计在 v0.8.2 里失效**（累计回源一直显示 0，而实际在回源）。要用容器层的数据：

```bash
# 看容器 CPU / 内存 / 网络
docker stats --no-stream --format '{{.CPUPerc}}  {{.MemUsage}}  {{.NetIO}}' iptv
```

`CPUPerc` 以**单核 100%** 为基准（所以 10% 表示用了 0.1 个核）。`NetIO` 是累计值，两次采样取差值就是速率。

测的时候注意：

1. 先在面板建好频道，确认能正常播放
2. 用多个播放器或脚本持续拉取该频道的播放地址
3. 间隔 20 秒以上采样两次，算差值
4. **区分冷/热缓存**：播过一次之后再测是热缓存；换新频道或清空缓存是冷缓存

面板内的实时指标仍可用于看 CPU 累计秒数和内存（这两个是准的），只有回源流量不准。

## 测试局限

说清楚这份数据的适用范围：

- 用的是 **VOD 点播流**，不是真直播。切片长度与刷新节奏和直播有差异
- 用 `curl` 模拟拉取，不是真实播放器（不发 Range 请求、不做缓冲策略）
- macOS 上测的，**Linux VPS 的 CPU 绝对值会有差异**，但相对关系（人数 vs 码率 vs 缓存）可用
- 实测回源流量为 3–13 MB/s，高于真实直播场景。原因是该测试的**缓存命中率偏低**。因此内存数值偏保守
- 未开启 Token、预载、录制、EPG 等功能。开启后会增加占用

**结论适用于「中低并发 + 单一代理模式」的容量规划。** 高并发（百人以上）或叠了录制、预载时，请以自己面板的实测读数为准。
